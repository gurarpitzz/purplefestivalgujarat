# Confirmed Architectural Decisions (Baseline Locked by Project Owner)

**Authority:** Section 1, Section 3, and Section 5 of the Master Implementation Directive (2026-11-26).  
**Rule:** These decisions are **CONFIRMED** and must not be re-asked or overridden without explicit new instruction from the Project Owner.

---

| ID | Confirmed Decision | Scope & Technical Implications | Supersedes |
|---|---|---|---|
| **CAD-01** | **Retain Native PHP + MySQL + PDO + Vanilla JS + HTML5/CSS3 Stack on Bluehost Apache / cPanel** | No rewrite to Next.js, React, Node backend, Laravel, or PostgreSQL. No Docker containers, Kubernetes, Redis, or persistent daemon servers. Local development and testing use native Windows XAMPP (`PHP 8.2.12` + `MariaDB 10.4.32` + `Apache 2.4.58`) with Bluehost cPanel Cron Jobs for asynchronous queue tasks. | Obsolete Next.js `README.md` & earlier Docker proposal |
| **CAD-02** | **Strictly Three Primary Participant Categories: `ATTENDEE`, `SLI`, `VOLUNTEER`** | Public registration presents only these 3 primary categories. Existing `DELEGATE`, `STUDENT`, `PROFESSIONAL`, `INSTITUTIONAL`, `ALLY`, and `ACCESSIBLE` categories are consolidated, migrated, or retired without destroying historical records. | Legacy 5-pathway hub / 8-category DB exposure |
| **CAD-03** | **Account-Based Participant Experience** | Public Website -> Login / Account Creation -> Authenticated Participant Account -> Category Selection (`ATTENDEE` / `SLI` / `VOLUNTEER`) -> Registration/Application -> Confirmation / Admin Review -> Authenticated Participant Dashboard. Returning participants can log in and view/manage their own records. | Commit `29e06db` staff-only login & passwordless anonymous `/apply` |
| **CAD-04** | **Three Primary Administrative Roles: `SUPERADMIN`, `ADMIN`, `REGISTRATION DESK` (`RGST`)** | Administrative roles remain strictly separate from participant registration categories. `SUPERADMIN` can create and assign configurable operational permission profiles within the `ADMIN` tier without granting unrestricted Superadmin authority. | Flat hardcoded `ADMIN` permissions |
| **CAD-05** | **Registration Desk (`/rgst`) Retained for Manual Attendance Marking** | Retain `/rgst` portal and `RGST` role to search registered Attendees, SLIs, and Volunteers and manually record physical attendance via accessible checkbox/toggle controls with atomic server-side persistence and duplicate prevention. | Earlier proposal to retire the entire `/rgst` portal |
| **CAD-06** | **Event-Day QR Scanning Discontinued** | Retire live camera (`html5-qrcode.min.js`) and USB QR scanning workflows from `/rgst`. Decouple attendance records from `qr_credentials` (key attendance on `registration_id` + scope/date, NOT `credential_id`). Retain `qrcode-gen.js` for Admin TOTP MFA and retain human-readable Registration IDs independently of QR. | Existing QR-mandatory `/rgst` scanner & `Action_Plan.pptx` Slide 9 QR entry model |
| **CAD-07** | **Accessibility Across All Three Categories (Not a 4th Category)** | Disability disclosure (always optional) and accommodation requests are integrated uniformly across `ATTENDEE`, `SLI`, and `VOLUNTEER`. Participants can request accommodations without disclosing a medical diagnosis. Target: WCAG 2.2 AA verified via automated + manual keyboard/screen-reader testing. | Standalone `ACCESSIBLE` hub card |
| **CAD-08** | **Preserve Existing Public Website Visual Identity** | Retain completed visual designs for Homepage, Viksit Bharat@2047, Partners (`#5B2A86`), 21 Specified Disabilities, Programme, Accessibility Guide, and Gallery. Make targeted edits only for content accuracy, WCAG 2.2 AA compliance, security fixes, and revised auth/registration links. | Any unnecessary frontend redesign |
| **CAD-09** | **No Hardcoded Planning Limits & Non-Destructive Data Preservation** | Festival estimates (5,000 attendees, 645 volunteers, 23 interpreters, 32 sessions, placeholder venues) are never hardcoded as fixed limits. Historical participant/credential/check-in records are never deleted to simplify migrations. | — |
| **CAD-10** | **Strict Evidence-Based Delivery & Phase-Gated Execution** | Every phase requires prerequisites, acceptance criteria, executed tests, regression checks, rollback plan, and a Section 9 Completion Report. Never claim `VERIFIED WORKING` without runtime test execution; never expose internal docs/audit files publicly; never send dev emails to real participants. | Previous unverified claims |
| **CAD-11** | **No Docker / No Container Dependency — Bluehost-Native Deployment & Verification** | Deployment must work directly via conventional Bluehost cPanel PHP/MySQL/Apache hosting (Resend API + cPanel Cron Jobs). Optional test tools (Playwright, Node.js, PHPUnit) are strictly dev/test-only and never production dependencies. Every Bluehost hosting assumption (PHP version, extensions, MySQL version, `.htaccess`, HTTPS, cron, private paths) must be verified via `scripts/verify-bluehost-env.php`. | Mandatory Docker Phase 1 acceptance criterion |
| **CAD-12** | **Approved Administrative MFA Policy (`D-20`)** | `SUPERADMIN` and `ADMIN` accounts have **mandatory TOTP MFA** (must complete enrollment before accessing protected admin APIs; self-disable prohibited). `RGST` has **optional MFA initially** with strong rate limiting, lockout, and CSRF protection. Uses 160-bit RFC 6238 secrets encrypted with AES-256-GCM, replay prevention, 8 single-use hashed recovery codes, and audited Superadmin-assisted recovery. Retains `assets/js/qrcode-gen.js` for MFA enrollment QR rendering. | Optional plaintext MFA (`FND-03`) |
| **CAD-13** | **Approved Discontinuation of New Participant Event-Entry QR Credentials (`D-01`)** | Discontinue new participant QR credential issuance across public registration and admin approval, remove QR pass images and third-party `api.qrserver.com` URLs from participant emails, and return `410 Gone` on retired QR issuance/verify/confirm endpoints. Retain human-readable Registration IDs (`PFG-2027-...`), historical `qr_credentials`/`checkins`/`credential_events` data, TOTP MFA QR enrollment, and public static QR links. | Automatic participant QR pass issuance & `api.qrserver.com` emails (`FND-06`) |
| **CAD-14** | **Controlled Versioned Migrations, Atomic InnoDB Numbering & Non-Destructive Consolidation (Phase 3)** | Zero per-request DDL in `includes/database.php`; all schema updates execute via checksummed CLI migrations (`database/migrate.php`, `schema_migrations`, `GET_LOCK`) portable across MySQL 8.0 and MariaDB 10.4+. Registration IDs (`PFG-2027-000001`) allocate atomically via InnoDB `AUTO_INCREMENT` (`registration_number_sequences`) decoupled from QR. All 6 legacy duplicate tables are archived read-only without dropping; `attendance_records` is decoupled from `qr_credentials`. | Ad-hoc per-request `ALTER TABLE`, `COUNT(*)+1` numbering race & dual-table UUID duplication (`FND-21`, `FND-29`) |
